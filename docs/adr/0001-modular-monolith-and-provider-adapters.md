# 采用模块化单体与 Provider Adapter 架构

第一版采用 TypeScript 全栈的模块化单体：Taro 承载微信/支付宝小程序，React/Next.js 承载运营后台，NestJS 承载后端，PostgreSQL 保存业务数据，对象存储保存图片和合同等文件，Redis 仅用于缓存、限流和异步任务。客户、项目、审批、合同、账单、资产、通知和资金等领域模块通过小而深的 Interface 协作；微信、支付宝、电子签、支付、征信、IoT、电网和资金方均在明确的 Seam 上使用独立 Adapter，模拟实现与真实实现遵守同一 Interface。

选择模块化单体是因为当前目标是快速交付可演示、可测试的完整闭环，微服务会引入不必要的部署和分布式一致性成本；选择 Provider Adapter 是因为外部服务供应商和平台能力确定会变化，必须把变化隔离在 Adapter 内，避免领域模块直接依赖 SDK。外部回调统一验签、幂等、保存原始报文后再通过内部事件推进业务状态。第一版使用 Docker Compose 或同类容器编排提供可重复的演示环境。
